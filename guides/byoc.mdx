If you are an AI agent, follow this prompt:

```markdown
Help me connect my own machines to Amika, so rigs can run on them.

If the `amika` CLI is not installed, or not logged in, first read
https://docs.amika.dev/guides/agent-quickstart and follow it to set it up.

Then read https://docs.amika.dev/guides/byoc and follow it to connect my
machines. On each machine, run `amika-hostd setup --skill` after the
install, and follow the instructions that it prints. Ask me before you turn
on a runtime or create an API key.
```

The rest of this page gives each step in more detail.

Bring your own compute (BYOC) runs rigs on machines that you control. You
install the `amika-hostd` daemon on a machine. The daemon registers the
machine with Amika as a **host**. Each rig that you create on the host runs
on that machine.

By default (`transport = "tunnel"`), the daemon connects out to Amika's
gateway. The machine needs no open port, so it works behind a home router or
a firewall. You can also [listen on a port](#listen-on-a-port-instead).

## Requirements

<Note>
- Linux x86_64 or arm64, or macOS. Linux VMs need glibc 2.34+ and KVM on
  Linux, or Apple silicon on macOS.
- Outbound HTTPS from the machine to Amika.
- A user-scoped Amika API key. Create one under **Settings → API Keys** at
  [app.amika.dev](https://app.amika.dev/settings/api-keys), or with the CLI
  during [setup](#set-up-a-host). A
  [listening host](#listen-on-a-port-instead) also accepts an organization
  key.
</Note>

## Set up a host

<Steps>

<Step title="Install the daemon">

On the machine that will run rigs:

```bash
curl -fsSL https://raw.githubusercontent.com/gofixpoint/amika/main/install-amika-hostd.sh | sh
```

The installer installs only `amika-hostd`, and Node.js if the machine does
not have it. It asks no questions. See [Installer options](#installer-options).

</Step>

<Step title="Set up the host">

```bash
amika-hostd setup
```

Setup asks for:

1. The host's name in Amika.
2. Your Amika API key.
3. The [runtimes](#runtimes) that the host runs. Each question says what it
   installs.

Setup then installs what each runtime needs, and writes the config file at
`~/.config/amika-hostd/config.toml`. It generates the secret key that Amika
uses to reach the daemon. Secrets go in the system keychain. On a server
with no keychain, set `secret_store = "file"` in the config file before you
run setup.

To set up without prompts, for a script or an AI agent, pipe the API key into
`setup --non-interactive`. Name the runtimes with `--enable` and `--disable`.
`amika auth api-key create` writes a new key to a file, and does not print it:

```bash
dir=$(mktemp -d)
amika auth api-key create --name my-host-hostd --scope user --out "$dir/api-key"
amika-hostd setup --non-interactive --hostname my-host --enable bare_metal < "$dir/api-key"
rm -rf "$dir"
```

`--non-interactive` asks nothing. It keeps a secret key that the host already
has. It stops, and changes nothing, if the hostname is not valid or no key
comes on stdin.

<Note>
`amika auth api-key create` needs amika CLI v0.24.0 or later. Sign in as
yourself (`amika auth login`): an organization key cannot create a user key.
Otherwise, create the key in the web UI, and save it to a file.
</Note>

<Tip>
`amika-hostd setup --skill` prints the steps that an AI agent follows to set
up the host. They include the transport, the runtimes, and how to get the API
key without seeing it.
</Tip>

</Step>

<Step title="Start the daemon">

To [listen on a port](#listen-on-a-port-instead), set `transport = "listen"`
in the config file first.

```bash
amika-hostd up
```

This registers the host with Amika, and connects the daemon to Amika's
gateway. Amika assigns the host's address, so you set up no URL. Pass `--fg`
to stay in the foreground.

</Step>

</Steps>

### Listen on a port instead

The daemon can listen on a port that you expose to the internet over HTTPS,
for example with [ngrok](https://ngrok.com) or
[Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/).
Put this line in the config file, above its first `[` line:

```toml
transport = "listen"
```

The daemon listens on `127.0.0.1:3020` by default. To change this, set `host`
and `port` in the config file, or pass `--host` and `--port` to `up`.

Expose the port, then start the daemon:

```bash
ngrok http 3020   # in another terminal; copy the https URL that it prints
amika-hostd up    # paste the URL when it asks
```

When the URL changes (a free ngrok URL changes on each restart), run
`amika-hostd register-url https://<public-url>`.

<Warning>
Register a bare HTTPS hostname, such as `https://hostd.example.com`, with no
path or port. Browsers open [previews](#previews-and-service-access) only on
such a host. Other URLs work to create and manage rigs.

Browser previews and `amika rig ssh` connect to the daemon directly at that
URL. Do not limit it to Amika's IP addresses, or put it behind an access gate.
</Warning>

## Create a rig on your host

<Tabs>

<Tab title="CLI">

```bash
# Make sure that the host registered, and see its sizes
amika host list

# Create a rig on it
amika rig create --name dev-box --host my-host --size small
```

`--size` takes one of the host's own sizes. Without `--host`, the rig runs on
Amika Cloud. On a host with more than one [runtime](#runtimes), `--runtime`
selects one (`smol`, `lume` or `bare_metal`). Without it, the rig uses its
preset's runtime. To start from a snapshot, add `--snapshot <name>`. The
snapshot must come from the same host (see
[Snapshots on your host](#snapshots-on-your-host)).

The first `amika-hostd up` downloads the preset images in the background. A
rig that you create before the download is done can time out. The daemon log
shows the progress.

</Tab>

<Tab title="Web UI">

1. Open **Create a rig** at [app.amika.dev](https://app.amika.dev).
2. Under **Runs on**, change **Amika Cloud** to **Your hosts**.
3. Select **VM**, or **Bare metal** for a [bare-metal rig](/guides/bare-metal-rigs).
4. Select your host and one of its sizes, then click **Create rig**.

A host that cannot take a rig stays in the list, but you cannot select it.
Each one shows why: **Not responding**, **No URL yet**, or **Checking…**.
When a host does not answer, the form tells why under the picker, with links
to **Manage hosts** and **check again**.

Your hosts are also under **Hosts** in the sidebar.

</Tab>

<Tab title="TypeScript">

Pass the host's ID as `hostId`. `amika host get <hostname>` prints it, and the
host's sizes.

```ts
const hostId = "host_123"; // From `amika host get my-host`
const rig = await client.rigs.create({ name: "dev-box", hostId, size: "small" });
await rig.wait();
```

With `hostId`, `size` is one of the host's own sizes. `rig.hostId` and
`rig.hostname` tell where a rig runs.

</Tab>

<Tab title="HTTP API">

Send the host's ID as `host_id`. `size` is then one of the host's sizes. To
select a [runtime](#runtimes), add `runtime` (`smol`, `lume` or `bare_metal`).

```bash
curl -X POST https://app.amika.dev/api/v0beta1/rigs \
  -H "Authorization: Bearer $AMIKA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"dev-box","host_id":"host_123","size":"small"}'
```

</Tab>

</Tabs>

## Runtimes

A runtime is how a host runs rigs. A host can have more than one.

| Runtime      | Rigs                                               | Machines                           | Setup installs |
| ------------ | -------------------------------------------------- | ---------------------------------- | -------------- |
| `smol`       | Linux VMs on smolvm (on by default)                | Linux (glibc 2.34+), Apple silicon | smolvm         |
| `lume`       | macOS VMs on [Lume](https://github.com/trycua/cua) | Apple silicon                      | Lume           |
| `bare_metal` | The host machine itself, as one rig                | Linux and macOS                    | `amikad`       |

Setup asks about each runtime that the machine can run. To change them later,
use one command. It installs what the runtime needs, updates the config file,
and reloads the running daemon:

```bash
amika-hostd capabilities update --enable lume
amika-hostd capabilities update --disable smol
```

Add `--dry-run` to see the plan first. The command does not turn off a
runtime that has rigs. `amika host list` shows each host's runtimes.

- **`smol`:** smolvm needs `resize2fs` (from `e2fsprogs`) to start a rig with
  a disk under 20 GiB. On Linux it also needs access to `/dev/kvm`. Setup
  tells you when one is missing, and how to fix it.
- **`lume`:** the daemon builds a macOS image in the background when it
  starts. This downloads a macOS restore image from Apple (about 20 GB),
  needs about 50 GB of free disk while it builds and 30 GB after, and takes
  30 minutes or more. Until the image is ready, the host refuses macOS rigs.
  Then create rigs with `--preset macos-coder`.
- **`bare_metal`:** see [Bare-metal rigs](/guides/bare-metal-rigs).

## Configure sizes and images

The config file sets the rig sizes that the host offers, and the image that
each preset starts. Each `amika-hostd up` sends the sizes to Amika, so the
file is the source of truth. The images stay on the host. After you edit the
file, restart the daemon.

```toml
[sizes.small]
vcpus = 2
memory_gib = 4
disk_gib = 20

[presets.coder.runtimes.smol]
image = "ghcr.io/gofixpoint/amika-coder:latest"
```

`:latest` follows each release. To keep a version, use a 12-character commit
SHA, such as `amika-coder:855d403678d5`.

<Note>
amika-hostd 0.7.0 and later do not start with the old `[preset_images]`
table. Run `amika-hostd config upgrade`, or `amika-hostd setup`, to change it.
</Note>

<Tip>
Keep `disk_gib` at 20 or more. Below 20, smolvm does not cache the rig's
image, so each create downloads it again.
</Tip>

## Snapshots on your host

You can [snapshot](/guides/create-a-snapshot) a rig that runs on your host.
The snapshot is a `.smolmachine` file on the host's disk. It can start new
rigs only on the same host.

- **Only snapshot and delete.** The daemon stops the rig to pack its disks,
  so **Snapshot everything**, which keeps the rig running, is not available.
- **Repository and organization default snapshots do not apply.** A host rig
  starts its preset image, unless you select one of the host's snapshots when
  you create it.
- **Snapshots are large.** Each one is several gigabytes. Set `snapshot_dir`
  in the config file (or `AMIKA_HOSTD_SNAPSHOT_DIR`) to a disk with space.
  The default is `~/.local/state/amika-hostd/snapshots`.

```toml
snapshot_dir = "/var/lib/amika-hostd/snapshots"
```

`amika snapshot list --long` shows a `HOST` column, which tells the host of
each snapshot.

## Previews and service access

Each [service](/reference/services) on a host rig gets a preview link. When
you open it, you sign in to Amika, and only members of your organization get
access. The link holds no credential, so a shared link gives no access. The
URL depends on the host's transport:

| Transport                             | Preview URL                                                                              |
| ------------------------------------- | ---------------------------------------------------------------------------------------- |
| `tunnel` (the default)                | Its own subdomain, `https://<service>--<rig>.r.<org>.o.amika.run/`                       |
| [`listen`](#listen-on-a-port-instead) | A path on your registered URL, `<registered-url>/v0beta1/rigs/<rig>/previews/<service>/` |

On a listening host, all previews share one origin and one sign-in:

- A page in one preview can act on each other preview that you opened there.
  Do not run code that you do not trust on that host.
- Open one preview at a time. Root-relative assets, such as those of a Vite
  or Next.js dev server, follow the preview that you opened last.

For scripts and tools such as `curl`, get a short-lived service token from
the HTTP API. It works only for rigs on your own hosts, never for `amikad`.

```bash
curl -X POST \
  "https://app.amika.dev/api/v0beta1/rigs/dev-box/services/web/tokens?ttl_seconds=900" \
  -H "Authorization: Bearer $AMIKA_API_KEY"
```

The response gives the service's `url`, the `header` for the token
(`X-Amika-Authorization`), the `token`, and `expires_at`. A token lasts one
hour by default, and one day at most.

```bash
curl -H "X-Amika-Authorization: Bearer $TOKEN" "$URL"
```

## Manage hosts

| Command                        | What it does                                   |
| ------------------------------ | ---------------------------------------------- |
| `amika host list`              | List your organization's hosts and their sizes |
| `amika host get <hostname>`    | Show one host, its ID, and its sizes           |
| `amika host delete <hostname>` | Delete a host and its stored secret            |

A host registers itself, so no command adds one. You cannot delete a host
that has rigs: delete the rigs first. You can also delete a host from
**Hosts** in the sidebar.

To take a host offline, run `amika-hostd down` on the machine. This stops the
daemon and its VMs, and keeps their disks. The next `up` starts the daemon,
but not the rigs: start them with `amika rig start`. If you delete only the
host record, the machine registers itself again on the next `amika-hostd up`.

### Rigs on a host that is gone

To delete a rig, its host must answer. When the host is offline, the delete
fails, and the web UI offers **Remove from Amika only**. This deletes Amika's
record of the rig. It does not stop what still runs on the machine: you clean
that up. The HTTP API does the same with
`DELETE /api/v0beta1/rigs/{id}?forget=true`.

## Uninstall the daemon

On the host, run the installer with `--uninstall`:

```bash
curl -fsSL https://raw.githubusercontent.com/gofixpoint/amika/main/install-amika-hostd.sh | sh -s -- --uninstall
```

The uninstaller does these steps:

1. Show what it found, and ask you to confirm.
2. Ask whether to remove the config and state directory, and the keychain
   secrets.
3. Stop the daemon, and delete the host's Lume rigs.
4. Ask you to type a phrase before it deletes the macOS images
   (`remove macos images`) or smolvm (`remove smolvm`).
5. Delete `amika-hostd` and its files, and what you said yes to.

It does not delete Lume or a downloaded macOS restore image, because other
tools can use them. It tells you where they are.

| Flag          | What it does                                                            |
| ------------- | ----------------------------------------------------------------------- |
| `--purge`     | Remove the config, state directory, and keychain secrets without asking |
| `--yes`, `-y` | Answer yes to each yes/no question. Use it when there is no terminal    |
| `--dry-run`   | Show what it would remove                                               |

No flag deletes smolvm or the macOS images.

<Warning>
Uninstalling changes nothing in Amika. The host stays registered, and its API
key still works. Delete the host with `amika host delete`, and revoke its API
key under **Settings → API Keys**.
</Warning>

## Installer options

| Flag                          | What it does                                                            |
| ----------------------------- | ----------------------------------------------------------------------- |
| `--install-version <version>` | Install a specific `amika-hostd` version                                |
| `--dry-run`                   | Show what it would do, and download or install nothing                  |
| `--uninstall`                 | Remove `amika-hostd`. See [Uninstall the daemon](#uninstall-the-daemon) |

Put flags after `sh -s --`, for example
`curl -fsSL .../install-amika-hostd.sh | sh -s -- --dry-run`.
`AMIKA_INSTALL_DIR` sets the launcher's directory (default `/usr/local/bin`).
`AMIKA_HOSTD_HOME` sets the directory for the daemon's files.
