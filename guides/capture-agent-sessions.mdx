here may change before general availability.
</Note>

Every Claude Code, Codex, OpenCode, or [`agent-send`](/guides/send-a-message-to-an-agent)
run produces a [session](/guides/manage-sessions). **Session capture** records
that session as a structured, queryable history — every message, tool call,
file edit, and git commit, along with the model used, token counts, and dollar
cost. The session id you get back from `agent-send` is the same id capture
records under.

Once captured, sessions become useful in three ways:

- **Cost and analytics.** See what your agents did and at what cost — sliced by user, repo, agent, or model.
- **Memory.** Search past work to recall how a similar problem was solved, what was decided, and which files were touched.
- **Mining.** Background jobs read past sessions to file follow-up tickets, encode user corrections into durable rules, and start parallel work.

Capture is agent-agnostic. Claude, Codex, and OpenCode sessions show up side
by side in the same list and timeline views.

## What gets captured

For each session, capture records:

- **Messages** — every turn, in order, with the author (which user sent it) and the source (web, Slack, or API).
- **Model and usage** — model name and version, input / output / cache-read / cache-write tokens, and dollar cost per message and per session.
- **Tool calls** — tool name, argument summary, outcome, and duration.
- **File changes** — repository, path, and change kind for every file the agent touched.
- **Git commits** — hash, branch, commit message, and the turn that produced each commit.
- **Errors** — where the agent got stuck, with surrounding context.
- **Environment** — agent CLI version, sandbox identifier, and the system prompt and rules in effect at run time.

These items share one ordered timeline. You can scrub through a session and
see, inline, the tool calls and file edits each message produced.

## Set up capture

Capture runs through a small companion CLI called `amikalog`. It ships
alongside the `amika` CLI — if you've installed `amika`, you already have
`amikalog`. Configuration is separate, but captured data is queried through
the same `amika sessions` commands described below.

### On your local machine

Initialize once:

```bash
amikalog init
```

`init` detects the agent CLIs already on your machine (Claude Code, Codex,
OpenCode) and the `amika sandbox agent-send` command, installs small
launcher shims on your `PATH`, and starts capturing each new session as it
runs. Sessions started before `amikalog init` are not retroactively
captured.

To stop capturing on this machine:

```bash
amikalog disable
```

### On an Amika sandbox

Sandboxes have `amikalog` pre-installed and capture enabled by default. To
turn it off for a sandbox, set `capture.enabled = false` in its
`.amika/config.toml`:

```toml
[capture]
enabled = false
```

## Where sessions are stored

Capture supports two sinks. Pick one at `init` time; switch later with
`amikalog init --sink ...`. Switching redirects new events — existing data
stays where it was written.

### Local files (default)

`amikalog` writes one JSONL file per session to
`~/.local/share/amikalog/sessions/`. Each line is a single event — a
message, tool call, file change, or commit. This sink is free, works
offline, and is easy to grep:

```bash
# Find every commit a session produced
jq 'select(.event_type == "commit")' \
  ~/.local/share/amikalog/sessions/3f2a....jsonl
```

Local-sink sessions are visible to the `amika sessions` CLI on the same
machine, but **not** to the web UI or to other people in your org.

<Info>
A SQLite sink is in the works for faster local querying. Until then, JSONL
plus `jq` or `grep` is the supported path.
</Info>

### Stream to Amika

Sign in with `amika auth login`, then re-init with the Amika sink:

```bash
amikalog init --sink amika
```

Events stream to Amika, where they're indexed and made available through
the web UI, the CLI, and search. Streamed sessions are reachable across
your machines and the rest of your organization, subject to your access
controls.

## View and use captured sessions

### In the web UI

When you stream to Amika, a **session browser** appears in
[app.amika.dev](https://app.amika.dev) under **Sessions**:

- **List view** — every session with its title, agent, repo and branch, status, cost, commit and file counts, participants, and timestamps. Filter by repo, agent, user, date, or cost.
- **Timeline view** — the event stream for a single session. Messages, tool calls, file changes, and commits inline in order. Each commit links to its diff or PR; each turn shows its own cost.
- **Cost dashboard** — spend by organization, user, repo, agent, and model over time.

### From the CLI

List recent sessions (works against either sink):

```bash
amika sessions list
```

Pull a session's filesystem locally — its messages, events, and any
artifacts it produced — to a directory you choose:

```bash
amika sessions fetch 3f2a... ./past-session
```

The fetched directory mounts cleanly into a new sandbox, so an agent in a
fresh sandbox can read past work as files:

```bash
amika sandbox create review-box \
  --mount ./past-session:/sessions/auth-refactor:ro
```

### From an agent

Capture exposes search and session-detail tools over MCP, so an agent or
background job can query prior sessions as part of its own run. See
[MCP integrations](/guides/mcp-integrations).

## Multi-user sessions

A single session can have more than one author. When two people drive the
same sandbox — for example, one from the web UI and one from Slack —
capture records which user sent each message and which surface it came
from. The session itself stays a single record; the per-message attribution
makes "who asked for what" answerable later.
