---
title: "Set up repo config with an agent"
description: "Have a coding agent analyze a repository and create its Amika rig configuration."
---

Use this guide from the repository you want to configure. Create only the
configuration the project needs. Do not invent services, ports, environment
variables, commands, or credentials.

This workflow targets hosted rigs. Before editing, read:

1. [How configuration works](/guides/configuration)
2. [config.toml reference](/guides/config-toml)
3. [Services](/reference/services)
4. [Rig environment presets](/reference/presets)
5. [Example config](https://github.com/gofixpoint/amika/blob/main/.amika/config.toml)

Work inside a temporary hosted rig so you can inspect the actual environment.
From an authenticated checkout, create one without running any existing setup
script:

```bash
amika auth status
amika rig create --no-setup --connect
```

Once connected, continue from the repository directory.

## 1. Investigate the repository

Inspect the repository before changing files.

### Languages and tools

- Identify each language, runtime, and package manager.
- Read version files, lock files, and package-manager configuration.
- Check `README.md`, `CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md`, `Makefile`,
  and equivalent development instructions.
- Read the existing `.amika/` directory, if present. Preserve valid settings
  and explain any setting you plan to remove or change.

Inspect the current rig instead of assuming tool versions:

```bash
for tool in git gh node npm pnpm python3 claude codex opencode pi docker; do
  if command -v "$tool" >/dev/null 2>&1; then
    printf '%s: ' "$tool"
    "$tool" --version 2>/dev/null | head -n 1 || true
  else
    printf '%s: not installed\n' "$tool"
  fi
done
```

The `coder` preset includes the standard development toolchain and the Claude
Code, Codex, OpenCode, and Pi CLIs. The `coder-plus-docker` preset adds Docker.
Use `coder` unless the project needs Docker inside the rig.

### Services

Find each development server, API, database, worker, or queue. Determine its
start command, port, protocol, health endpoint, and whether it must start
automatically. Check package scripts, source defaults, Docker files, Compose
files, and process-manager configuration.

### Environment and secrets

- Ask the user how the project stores secrets.
- Find environment-variable reads and example env files.
- Separate secrets, required non-secret configuration, and optional settings.
- Do not request or read secret values.
- Use an `[env]` secret reference for every environment-variable secret.
- Preserve an existing encrypted-secret-file workflow. Never add an untracked
  secret file to Git. Tell the user about any manual copy or decryption step.

## 2. Confirm the plan

Before editing, briefly report:

1. The detected runtimes and missing tools.
2. The recommended preset and size.
3. Each service, its port, URL scheme, start command, and health check.
4. Each required environment variable and whether it is secret.
5. The install, build, migration, and service-start commands.

Ask only the questions needed to resolve uncertainty. Do not read or push
secrets. List the `amika secret push` commands the user must run.

## 3. Create the configuration

Create `.amika/config.toml` and any required scripts under `.amika/scripts/`.
A typical hosted configuration looks like this:

```toml
[sandbox]
preset = "coder"
size = "a1.medium"

[lifecycle]
setup_script = ".amika/scripts/setup.sh"
start_script = ".amika/scripts/start.sh"

[services.web]
port = 3000
url_scheme = "http"

[env]
NODE_ENV = "development"
API_KEY = { secret = "project-api-key" }
```

Add only the sections the repository needs.

### Sandbox settings

- Valid presets are `coder` and `coder-plus-docker`.
- Use `coder-plus-docker` only when the project needs Docker inside the rig.
- A1 sizes are `a1.tiny`, `a1.small`, `a1.medium`, `a1.large`, and
  `a1.xlarge`. Recommend `a1.medium` unless the repository needs a different
  size. The selected provider must offer that size.
- `coder-plus-docker` does not support the smallest size tier, including
  `a1.tiny`.
- An optional `snapshot` value selects a repository snapshot by its friendly
  label.

### Lifecycle scripts

- `setup_script` runs during initial rig creation.
- `start_script` runs when a stopped rig starts again, not during creation.
- Include a shebang and `set -euo pipefail` in every script.
- Use `$AMIKA_AGENT_CWD` for the primary repository path.
- Exit nonzero on failure. Amika records the failure and keeps the rig
  accessible.
- The executable bit in Git is not required.

Keep one-time installation and build work in `setup.sh`. If services must run
after both creation and restart, invoke a shared startup script from both
lifecycle scripts.

Example `setup.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

cd "$AMIKA_AGENT_CWD"

# Install missing system tools and project dependencies.
# Run required builds, code generation, and migrations.

bash "$AMIKA_AGENT_CWD/.amika/scripts/start-services.sh"
```

Example `start.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

bash "$AMIKA_AGENT_CWD/.amika/scripts/start-services.sh"
```

Use systemd units when long-running services need supervision and logs.

### Services and environment

- Use `[services.<name>]` for named service definitions.
- Use `port` for one binding or `ports` for multiple bindings.
- Integer ports use TCP. A string can specify a protocol, such as
  `"4982/udp"`.
- Add `url_scheme = "http"` or `"https"` only for services that speak that
  protocol.
- Do not use ports 60899 through 60999. Amika reserves them.
- Environment-variable names must match `^[A-Z_][A-Z0-9_]*$`.
- A secret reference uses `{ secret = "secret-name" }`.
- A service reference uses
  `{ service = "service-name", field = "url" | "host" | "port" }`.

Optional hosted sections include `[filesystem]` for additional repositories,
`[agent_credentials]` for Claude or Codex credentials, and `[workflow]` for a
multi-step agent workflow. Read the config reference before using them.

## 4. Verify the result

Before reporting completion:

1. Parse the TOML:

   ```bash
   python3 -c 'import pathlib, tomllib; tomllib.loads(pathlib.Path(".amika/config.toml").read_text())'
   ```

2. Run `bash -n` on every shell script.
3. Confirm that every referenced file exists.
4. Confirm that service ports match their start commands.
5. Confirm that every secret uses a secret reference.
6. Confirm that no service uses a reserved port.
7. Run `git diff --check`.

List the required secret names without requesting their values. Give the user
one command per secret:

```bash
amika secret push SECRET_NAME=value
```

Summarize the generated files, preset, size, services, and untested
assumptions.

## 5. Test the configuration

Hosted rigs clone the remote repository, so commit and push the changes:

```bash
git add .amika
git commit -m "Add Amika rig configuration"
git push
```

Ask the user to push every referenced secret before creating the test rig:

```bash
amika secret push SECRET_NAME=value
```

Create a named rig, then connect to it:

```bash
amika rig create --name repo-config-test
amika rig ssh repo-config-test
```

Inside the rig, check each service with its process manager and local health
endpoint. For a systemd service:

```bash
sudo systemctl status SERVICE_NAME
sudo journalctl -u SERVICE_NAME --no-pager -n 100
curl -fsS http://127.0.0.1:3000/health
```

From an authenticated machine, inspect published bindings and URLs. This does
not check process health:

```bash
amika service list --rig-name repo-config-test
```

Use a [service reference](/guides/config-toml#service-reference) when an
environment variable needs a rig service's public URL, host, or port.
