Use a coding agent such as Claude Code, Codex, OpenCode, or Pi to analyze a
repository and create its `.amika/config.toml` and lifecycle scripts.

This workflow targets hosted rigs. It uses CLI commands that an agent can run.

## Prepare a setup rig

From the repository you want to configure, confirm that the CLI is authenticated:

```bash
cd /path/to/repo
amika auth status
```

If necessary, authenticate before continuing:

```bash
amika auth login
```

Create a rig without running the repository's existing setup script, then
connect to it:

```bash
amika rig create --no-setup --connect
```

In the rig, open your coding agent from the repository directory and give it
the prompt below.

## Agent prompt

Copy and paste this prompt into the coding agent:

````markdown
# Set up Amika repository configuration

Create an Amika configuration for this repository. The result must provision a
hosted rig with the project's dependencies, environment, and development
services.

Create only the configuration the repository needs. Do not invent services,
ports, environment variables, commands, or credentials.

## Reference material

Read these sources before editing:

1. [How configuration works](https://docs.amika.dev/guides/configuration)
2. [config.toml reference](https://docs.amika.dev/guides/config-toml)
3. [Services](https://docs.amika.dev/reference/services)
4. [Rig environment presets](https://docs.amika.dev/reference/presets)
5. [Example config](https://github.com/gofixpoint/amika/blob/main/.amika/config.toml)

The task-specific rules are also summarized below. If the docs and this prompt
disagree, call out the conflict and prefer the current Amika docs.

## 1. Investigate the repository

Inspect the repository before changing files.

### Languages and tools

- Identify each language, runtime, and package manager.
- Read version files such as `.nvmrc`, `go.mod`, `pyproject.toml`,
  `rust-toolchain.toml`, and `Gemfile`.
- Read lock files and package-manager configuration.
- Check `README.md`, `CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md`, `Makefile`,
  and equivalent development instructions.

### Existing Amika configuration

- Read the existing `.amika/` directory, if present.
- Preserve valid settings unless the user asks to replace them.
- Explain any existing setting you plan to remove or change.

### Installed rig tools

Inspect the current rig instead of assuming exact tool versions:

```bash
for tool in git gh node npm pnpm python3 claude codex opencode pi docker; do
  if command -v "$tool" >/dev/null 2>&1; then
    printf '%s: ' "$tool"
    "$tool" --version 2>/dev/null | head -n 1 || true
  else
    printf '%s: not installed\n' "$tool"
  fi
done
```

The `coder` preset includes the standard development toolchain and the Claude
Code, Codex, OpenCode, and Pi agent CLIs. The `coder-plus-docker` preset adds
Docker. Recommend `coder` unless the project needs Docker inside the rig.

### Services

- Find each development server, API, database, worker, or queue.
- Find its start command, port, protocol, and health endpoint.
- Check package scripts, source defaults, Docker files, Compose files, and
  existing process-manager configuration.
- Distinguish processes that must start automatically from commands that a
  developer runs manually.

### Environment and secrets

- Ask the user how they store secrets. Use this info to decide how to get
  secrets into the config or onto the rig.
- Find environment-variable reads and example env files.
- Separate required secrets, required non-secret configuration, and optional
  settings.
- Never directly read a secret value or put one in plaintext in
  `.amika/config.toml` or commit one to Git.
- Use an `[env]` secret reference for every secret.
- In some cases, users might have an file with encrypted secrets in it, which
  can just be copied into a Rig, or sometimes is checked into the Git repo
  itself.  If they haven't checked in this file to the repo, DO NOT check it in
  yourself.

## 2. Confirm the plan

Before editing, show the user:

1. The detected runtimes and missing tools.
2. The recommended preset and size.
3. Each service, its port, URL scheme, start command, and health check.
4. Each required environment variable and whether it is secret.
5. The install, build, migration, and service-start commands you plan to use.

Be concise. Ask only the questions needed to resolve uncertainty.  user for
secret values. Do not automatically read or push secrets yourself. Tell them
which `amika secret push` commands they must run.

## 3. Create the configuration

Create `.amika/config.toml` and the required scripts under `.amika/scripts/`.

A typical hosted configuration looks like this:

```toml
[sandbox]
preset = "coder"
# #amika/annotate "this is an outdated size. Use a1.* sizes"
size = "m"

[lifecycle]
setup_script = ".amika/scripts/setup.sh"
start_script = ".amika/scripts/start.sh"

[services.web]
port = 3000
url_scheme = "http"

[env]
NODE_ENV = "development"
API_KEY = { secret = "project-api-key" }
```

Add only the sections the repository needs.

### Sandbox settings

- Valid presets are `coder` and `coder-plus-docker`.
- Use `coder-plus-docker` only when the project needs Docker inside the rig.
<!-- #amika/annotate "this is an outdated size. Use a1.* sizes" -->
- The friendly size aliases are `xs`, `m`, `l`, and `xl`. The API also accepts
  versioned sizes such as `a0.m` and `a1.medium` when the selected provider
  offers them.
- `coder-plus-docker` does not support the `xs` tier.
- Recommend `m` unless the repository clearly needs a different size.
- An optional `snapshot` value is a repository snapshot's friendly label.

### Lifecycle scripts

- `setup_script` runs during initial rig creation.
- `start_script` runs when a stopped rig starts again. It does not run during
  initial creation.
- Amika reads repository lifecycle scripts as file contents. Their executable
  bit in Git is not required.
- Give every script a shebang and `set -euo pipefail`.
- Use `$AMIKA_AGENT_CWD` for the primary repository path.
- Exit nonzero when setup fails. The rig remains accessible, but Amika records
  the setup failure.

Keep one-time installation and build work in `setup.sh`. If services must run
after both creation and restart, put their startup logic in a shared script and
invoke it with `bash` from both lifecycle scripts.

Example `setup.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

cd "$AMIKA_AGENT_CWD"

# Install missing system tools.
# Install project dependencies.
# Run required builds, code generation, and migrations.

bash "$AMIKA_AGENT_CWD/.amika/scripts/start-services.sh"
```

Example `start.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

bash "$AMIKA_AGENT_CWD/.amika/scripts/start-services.sh"
```

For long-running services, you can use systemd unit files.

### Services and environment

- Use `[services.<name>]` for named service definitions.
- Use `port` for one binding or `ports` for multiple bindings.
- Integer ports use TCP. A string can specify a protocol, such as
  `"4982/udp"`.
- Add `url_scheme = "http"` or `"https"` only for services that speak that
  protocol.
- Do not use ports 60899 through 60999. Amika reserves them.
- Environment-variable names must match `^[A-Z_][A-Z0-9_]*$`.
- A secret reference uses `{ secret = "secret-name" }`.
- A service reference uses
  `{ service = "service-name", field = "url" | "host" | "port" }`.

Optional hosted sections include:

- `[filesystem]` with `repos` for additional repositories.
- `[agent_credentials]` for default Claude or Codex credentials.
- `[workflow]` for a repository-defined multi-step agent workflow.

Read the config reference before adding any optional section.

## 4. Verify the result

Before reporting completion:

1. Parse the TOML:

   ```bash
   python3 -c 'import pathlib, tomllib; tomllib.loads(pathlib.Path(".amika/config.toml").read_text())'
   ```

2. Run `bash -n` on every shell script.
3. Confirm that every referenced file exists.
4. Confirm that service ports match the commands that start them.
5. Confirm that every secret uses a secret reference.
6. Confirm that no service uses a reserved port.
7. Run `git diff --check`.

List the required secrets without requesting their values. Give the user a
command for each one:

```bash
amika secret push SECRET_NAME=value
```

Summarize the generated files, the selected preset and size, the services that
will start, and any assumptions that still need testing.
````

## Test the generated configuration

Review the agent's changes. Then commit and push them because hosted rigs clone
the repository from its remote:

```bash
git add .amika
git commit -m "Add Amika rig configuration"
git push
```

Push each secret referenced by the config:

```bash
amika secret push SECRET_NAME=value
```

Create and connect to a new rig:

```bash
amika rig create ${new-rig-name}
amika rig ssh ${new-rig-name}
```

Inside the rig, verify that each service is running. Use systemd to check health
and to check logs. You can hit their ports on localhost inside the rig, or use
`amika service list --rig-name $AMIKA_RIG_NAME` to find public URLs of those
services. If `$AMIKA_RIG_NAME` is not defined within the rig's environment,
check `$AMIKA_SANDBOX_NAME`.

## Gotchas

- Sometimes you need an environment variable that dynamically refers to values from the rig or its services. For example, if you need the public URL of a service running from a rig so you can use it as a webhook. You can use "service reference" environment variables for this: https://docs.amika.dev/guides/config-toml#service-reference
