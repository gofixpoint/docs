## Agent credential setup

For remote sandboxes, you can push Claude Code or Codex credentials to the Amika secrets store and have them automatically injected at sandbox creation time. This avoids manual authentication inside the sandbox.

See [CLI reference](/reference/cli-reference) for the full `amika secret claude` and `amika secret codex` flag references.

## Push Claude credentials

### OAuth Workflow (preferred)

1. **Push credentials** from your local machine:

```bash
# Specify the "oauth" type and amika will auto-detect and store your credential in the secret vault
amika secret claude push --type oauth
```

2. The OAuth credential is auto-set inside the sandbox's Claude settings, so you can just run `claude` without having to log in again.

### API Key Workflow

1. **Push credentials** from your local machine:

```bash
# Interactive discovery (scans Claude config files and macOS keychain)
amika secret claude push

# Or specify directly
amika secret claude push --type api_key --value sk-ant-xxx
```

2. **Inject when creating a sandbox** — select a credential via the web UI, or use the `--secret` flag:

```bash
amika sandbox create --git --remote --secret env:ANTHROPIC_API_KEY=my-claude-key
```

3. Claude Code is pre-authenticated inside the sandbox — no manual login needed.

## Push Codex credentials

Codex credentials work the same way as Claude. `amika secret codex push` scans `~/.codex/auth.json` and lets you pick which credential to push.

### OAuth Workflow

```bash
# Auto-detect and push OAuth tokens from ~/.codex/auth.json
amika secret codex push --type oauth
```

The OAuth credential is auto-set inside the sandbox's Codex settings, so `codex` runs without re-authenticating.

### API Key Workflow

```bash
# Interactive discovery
amika secret codex push

# Auto-resolve by type — reads OPENAI_API_KEY, falls back to ~/.codex/auth.json
amika secret codex push --type api_key

# Or specify directly
amika secret codex push --type api_key --value sk-...
```

Inject into a sandbox by selecting the credential in the web UI or via `--secret`:

```bash
amika sandbox create --git --remote --secret env:OPENAI_API_KEY=my-codex-key
```

## Pin a credential at sandbox creation

If you have multiple credentials pushed for the same agent kind (for example,
both an OAuth and an API-key credential for Claude), you can tell the CLI
which one to inject when you create a sandbox. This is the way to keep
scripted flows deterministic instead of relying on default selection.

| Flag | Format | Behavior |
| --- | --- | --- |
| `--agent-credential <KIND=NAME>` | `claude=personal-oauth` | Pick the stored credential by name |
| `--agent-credential-type <KIND=TYPE>` | `claude=oauth` or `claude=api-key` | Pick by credential type and let the server choose a matching credential |
| `--no-agent-credential <KIND>` | `codex` | Skip credential injection for that kind entirely |

Examples:

```bash
# Pin Claude to a specific stored credential by name
amika sandbox create --git --remote \
  --agent-credential claude=personal-oauth

# Pin Claude to whatever API-key credential is available
amika sandbox create --git --remote \
  --agent-credential-type claude=api-key

# Use Claude defaults but skip injecting any Codex credential
amika sandbox create --git --remote \
  --no-agent-credential codex
```

<Note>
Supported kinds are `claude` and `codex`. Type values are `oauth` or
`api-key`. Each flag may appear at most once per kind, and
`--no-agent-credential` is mutually exclusive with the other two for the
same kind. You can combine `--agent-credential` and `--agent-credential-type`
on the same kind to pin both name and type. See
[CLI reference](/reference/cli-reference#create-flags) for the full flag
table.
</Note>

## Credential discovery

`amika auth extract` discovers locally stored API credentials from multiple coding agent tools and prints them as shell environment assignments.
You can use this to copy coding agent credentials into Amika's web UI so you can
spin up ready-to-go sandboxes from the web.

### Quick start

```bash
# Print detected assignments
amika auth extract

# Export into current shell
eval "$(amika auth extract --export)"

# Skip OAuth sources
amika auth extract --no-oauth
```

### Supported sources

Amika reads sources in priority order.

| Priority | Source | Files | Providers |
| --- | --- | --- | --- |
| 500 | Claude API key | `~/.claude.json.api`, `~/.claude.json` | Anthropic |
| 400 | Claude OAuth | `~/.claude/.credentials.json`, `~/.claude-oauth-credentials.json` | Anthropic |
| 300 | Codex | `~/.codex/auth.json` | OpenAI |
| 290 | Amika env cache | `${XDG_CACHE_HOME}/amika/env-cache.json` | Any |
| 280 | Amika keychain | `${XDG_DATA_HOME}/amika/keychain.json` | Any |
| 270 | Amika OAuth | `${XDG_STATE_HOME}/amika/oauth.json` | Any |
| 200 | OpenCode | `~/.local/share/opencode/auth.json` | Any |
| 100 | Amp | `~/.amp/config.json` | Anthropic |

Higher-priority sources win when multiple files provide the same provider key.

### Output mapping

Amika normalizes provider names and exports common aliases:

- Anthropic keys output as both `ANTHROPIC_API_KEY` and `CLAUDE_API_KEY`.
- OpenAI keys output as both `OPENAI_API_KEY` and `CODEX_API_KEY`.

Example output:

```bash
ANTHROPIC_API_KEY='sk-ant-...'
CLAUDE_API_KEY='sk-ant-...'
OPENAI_API_KEY='sk-...'
CODEX_API_KEY='sk-...'
```

### Provider canonicalization

Provider names are normalized before deduplication:

- `claude`, `anthropic` → `anthropic`
- `codex`, `openai` → `openai`
- Other providers are lowercased, with separators normalized to hyphens

### OAuth token handling

OAuth sources (`claude_oauth`, `amika_oauth`, Codex OAuth, OpenCode OAuth) are included by default. Use `--no-oauth` to skip them.

OAuth tokens with an `expiresAt` or `expires` timestamp are skipped if expired.

### Flags

| Flag | Default | Description |
| --- | --- | --- |
| `--export` | `false` | Prefix lines with `export` |
| `--homedir <path>` | `$HOME` | Override home directory for discovery |
| `--no-oauth` | `false` | Skip OAuth credential sources |

<Tip>
Use `--homedir` in CI or test environments when you need deterministic credential fixtures.
</Tip>
