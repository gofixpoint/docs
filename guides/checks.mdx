A check is an executable program that runs against your repository inside an
Amika sandbox. Checks can inspect the code, run tests or static analysis,
and optionally commit fixes back to the branch. Each check is just a file —
a shell script, a Node program, a Python tool — that you drop into
`.amika/checks/` at the root of your repo.

Checks are designed to compose like UNIX tools, not configure like a CI
YAML. If you can write a script, you can write a check.

## How checks run

When a check is triggered, Amika spins up a sandbox loaded with your repo
at the relevant branch, runs the check file, and collects its results.

Each executable file inside `.amika/checks/` runs in its own sandbox. If
you have three check files, you get three parallel sandboxes per trigger.

A check can be triggered from three places:

| Trigger | When it runs |
| --- | --- |
| **GitHub PR** | On every push to a pull request branch |
| **Git hook** | Pre-commit or pre-push on your local machine |
| **Agent hook** | After a coding agent finishes a turn inside a sandbox |

<Note>
Two CLIs come up in this guide. `amika` runs on your host machine and
manages sandboxes, hooks, and config. `amikactl` runs **inside** the
sandbox and lets a running check talk to the runner — to report progress,
log output, or attach artifacts. Anything you run from your terminal is
`amika`; anything inside a check script is `amikactl`.
</Note>

## Write your first check

Create a `.amika/checks/` directory at the root of your repo and drop an
executable file inside it. Anything with the executable bit set is treated
as a check.

```bash
mkdir -p .amika/checks
cat > .amika/checks/lint.sh <<'EOF'
#!/bin/bash
set -e

amikactl check step "install"
npm ci

amikactl check step "lint"
npm run lint
EOF
chmod +x .amika/checks/lint.sh
```

The `amikactl check step` calls are optional but recommended — they give
the runner structured progress that surfaces in the PR check UI. Without
them, the runner only sees the final exit code.

A non-zero exit fails the check. Anything written to stdout and stderr is
captured as the check log.

## Make a check that commits fixes

A check can modify files in the sandbox's working copy. By default those
changes stay in the sandbox and are discarded when the check finishes. To
push them back to the branch, declare the check's commit behavior in
`.amika/checks/config.toml`:

```toml
[check."format.sh"]
display_name = "Format code"
description = "Runs prettier and commits any changes."
commit_mode = "auto"
```

`commit_mode` has three values:

| Value | Behavior |
| --- | --- |
| `"none"` (default) | Changes stay in the sandbox and are discarded |
| `"auto"` | Changes are committed to the PR branch and pushed |
| `"staging"` | Changes go to a per-PR, per-check staging branch you can merge back into the PR branch after review |

`"staging"` is the safer option for checks that rewrite code with an
agent — you see the diff before it lands on the PR branch.

## Stop runaway loops

A check with `commit_mode = "auto"` can re-trigger itself by pushing
commits that re-fire the PR check. Every check has a `loop_limit` to cap
how many times this can happen on a single PR:

```toml
loop_limit = 5

[check."format.sh"]
loop_limit = 2
```

The top-level `loop_limit` applies to every check; per-check entries
override it. Once a check hits its limit, the runner stops re-triggering
it for that PR and reports the check as **halted** with a warning in the
GitHub check UI (neutral status — not pass, not fail). Other checks keep
running normally.

## Configure individual checks

`.amika/checks/config.toml` lets you attach metadata to each check without
changing the script itself.

```toml
[check."test.sh"]
display_name = "Unit tests"
description = "Runs the Jest suite against the PR branch."
size = "m"
loop_limit = 1
```

| Field | Type | Purpose |
| --- | --- | --- |
| `display_name` | string | Name shown in the PR check UI |
| `description` | string | Subtitle shown alongside the check |
| `size` | `"xs"`, `"s"`, `"m"`, `"l"` | Sandbox size for this check |
| `commit_mode` | `"none"`, `"auto"`, `"staging"` | What to do with file changes |
| `loop_limit` | integer | Max re-triggers per PR before the runner stops |

## Run checks locally

The same checks can run on your machine through git hooks or as an agent
hook. Initialize the hooks with:

<CodeGroup>

```bash Git hooks
amika checks init githooks
```

```bash Agent hooks
amika checks init agenthooks
```

</CodeGroup>

`init githooks` installs a pre-commit hook that runs every check in
`.amika/checks/`. `init agenthooks` registers a hook with your local agent
(Claude Code, Codex, OpenCode) so checks run after each agent turn. Both
modes reuse the same per-check sandbox execution as the PR check.

## Security

The PR check runner has two hard rules:

<Warning>
Checks **do not run on PRs from forks**, and **do not run for users
outside your Amika org**. This is non-negotiable — a check that runs
arbitrary code from an untrusted contributor would be a remote code
execution vector.
</Warning>

If you need to run checks against contributions from outside your org, run
them locally on a maintainer's machine after review.

## End-to-end example

A repo that uses two checks — formatting with auto-commit, and tests in
read-only mode:

```
my-repo/
├── .amika/
│   ├── config.toml
│   └── checks/
│       ├── config.toml
│       ├── format.sh
│       └── test.sh
└── src/...
```

```toml .amika/checks/config.toml
loop_limit = 3

[check."format.sh"]
display_name = "Format code"
commit_mode = "auto"
loop_limit = 2

[check."test.sh"]
display_name = "Unit tests"
size = "m"
```

```bash .amika/checks/format.sh
#!/bin/bash
set -e
amikactl check step "format"
npm run format
```

```bash .amika/checks/test.sh
#!/bin/bash
set -e
amikactl check step "test"
npm test
```

When you push a PR, two sandboxes spin up in parallel. `format.sh`
reformats files and pushes the change back to the PR branch. `test.sh`
runs the suite and surfaces failures in the check log. If `format.sh`
keeps finding new things to fix, it stops after two re-runs.
